# Module 06 — Notifications

## Status

Not started. Spec recorded here for later implementation.

> **Decision:** Notifications are an in-app delivery layer for important
> events produced by other modules.
>
> Notifications do not own business state or business transitions.
>
> Jobs, Proposals, and future modules own the events. Notifications stores and
> delivers those events to the appropriate users.

---

# Purpose

The Notifications module informs users when an important event has occurred.

Example:

```text
Provider submits Proposal
        ↓
Proposals module
        ↓
ProposalSubmitted event
        ↓
Notifications module
        ↓
Client receives notification
```

The module provides an in-app notification center with:

- Notification creation
- Notification listing
- Read/unread state
- Mark as read
- Mark all as read
- Notification metadata
- Deep-link information

---

# Goals

- Store notifications for authenticated users
- Deliver notifications generated by supported domain events
- Show unread notifications
- Allow users to mark notifications as read
- Allow users to mark all notifications as read
- Preserve notification history
- Provide enough metadata for frontend navigation
- Prevent users from accessing another user's notifications
- Keep notification creation separate from business logic
- Provide a reusable notification mechanism for future modules

---

# Non Goals

The following are intentionally excluded from Phase 1:

- Email notifications
- SMS notifications
- Push notifications
- WhatsApp notifications
- Browser push
- Notification preferences
- Digest notifications
- Scheduled notifications
- Notification queues
- Redis
- Kafka
- Event bus infrastructure
- Background workers
- AI-generated notification content
- Marketing notifications
- Recommendation notifications
- Advanced notification templates

# Responsibilities

The module is responsible for:

- Notification persistence
- Notification creation
- Notification retrieval
- Read/unread state
- Notification authorization
- Notification type definitions
- Notification metadata
- Notification retention rules

The module is NOT responsible for:

- Deciding when a Job becomes published
- Deciding when a Proposal is accepted
- Deciding when a Connection is established
- Changing Job state
- Changing Proposal state
- Creating business entities
- Authentication
- Authorization of the underlying business operation

# Core Concept

Notifications are **derived information**.

For example:

```text
Proposal
  ↓
ACCEPTED
  ↓
ProposalAccepted event
  ↓
Notification created
```

The notification does not cause the Proposal to become accepted.

The Proposal acceptance happens first.

Then the notification is generated.

# Database Design

## Notification

Purpose:

Stores an in-app notification for one recipient.

Contains:

- ID
- Recipient User ID
- Type
- Title
- Message
- Data
- Read At
- Created At

Suggested structure:

```text
Notification

id
recipientUserId
type
title
message
data
readAt
createdAt
```

---

# Notification Type

Use a controlled enum.

Phase 1:

```text
PROPOSAL_SUBMITTED
PROPOSAL_WITHDRAWN
PROPOSAL_ACCEPTED
PROPOSAL_REJECTED
CONNECTION_ESTABLISHED
JOB_CANCELLED
```

Do not allow arbitrary notification types from API requests.

---

# Notification Data

`data` stores machine-readable context needed by the frontend.

Example:

```json
{
  "proposalId": "uuid",
  "jobId": "uuid"
}
```

For Connection:

```json
{
  "connectionId": "uuid",
  "jobId": "uuid",
  "proposalId": "uuid"
}
```

The frontend can use this information to navigate the user to the relevant resource.

---

# Important Rule

Do not put sensitive business data into `data`.

For example, don't store:

```json
{
  "clientPassword": "...",
  "privateDocumentUrl": "...",
  "paymentToken": "..."
}
```

Notification metadata should contain IDs and safe navigation information.

# Pagination

Notification lists must be paginated.

Example:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 42,
    "totalPages": 3,
    "hasNext": true,
    "hasPrevious": false
  }
}
```

Default ordering:

```text
createdAt DESC
id DESC
```

The ID acts as a deterministic tiebreaker.

---

# Notification Listing Rules

The authenticated user can only retrieve:

```text
notification.recipientUserId
=
authenticatedUser.id
```

Never accept:

```text
GET /notifications?userId=someone-else
```

as an authorization mechanism.

The recipient is always derived from authentication.

---

# Read State

Unread:

```text
readAt = NULL
```

Read:

```text
readAt = timestamp
```

This is preferable to a boolean because it records when the notification was read.

---

# Mark as Read

Valid:

```text
UNREAD
  ↓
READ
```

Repeated calls should be safe.

If a notification is already read:

```text
PATCH /notifications/:id/read
```

should not create another state or error unnecessarily.

It can simply return the already-read notification.

---

# Mark All as Read

Only update:

```text
recipientUserId = authenticatedUser.id
AND
readAt IS NULL
```

Do not update notifications belonging to other users.

---

# Notification Creation

Notifications should be created by application services after successful domain operations.

Example:

```text
ProposalService
    ↓
acceptProposal()
    ↓
transaction succeeds
    ↓
ProposalAccepted
    ↓
NotificationService
    ↓
create notification
```

The notification must not be created before the business operation successfully commits.

---

# Transaction Boundary

For Phase 1:

```text
Business transaction
      ↓
COMMIT
      ↓
Create notification
```

If the notification fails, the underlying business operation must not be rolled back merely because an in-app notification could not be stored.

Example:

```text
Proposal accepted
      ↓
Transaction succeeds
      ↓
Notification creation fails
      ↓
Proposal remains ACCEPTED
```

This is intentional.

Notifications are secondary delivery state.

---

# Idempotency

Duplicate domain-event delivery must not create unlimited duplicate notifications.

Example:

```text
ProposalAccepted
ProposalAccepted
```

should not necessarily produce:

```text
Notification
Notification
```

For events that may be retried, notification creation should use a stable event identifier.

Recommended future-compatible fields:

```text
eventId
```

and:

```text
sourceType
sourceId
```

**[Decision]** If the current architecture has no event infrastructure, Phase 1 may initially create notifications directly from services. However, the schema should be designed so an event identifier can be added without redesigning the entire module.

---

# Notification Authorization

Users may:

- Read their own notifications
- Mark their own notifications as read
- Mark all their notifications as read

Users may NOT:

- Read another user's notifications
- Mark another user's notifications as read
- Create notifications for themselves through the public API
- Change notification type
- Change recipient
- Change notification ownership

Notification creation is an internal server operation.

There should be **no public endpoint such as**:

```text
POST /notifications
```

for normal users.

---

# Security

## IDOR Prevention

This must be enforced:

```text
Authenticated User
        ↓
Notification.recipientUserId
        ↓
Must match
```

Never trust a `userId` supplied by the client.

---

## Mass Assignment

The client must never be allowed to submit:

```json
{
  "recipientUserId": "...",
  "type": "PROPOSAL_ACCEPTED",
  "readAt": "...",
  "data": {}
}
```

through a public notification creation endpoint.

Notification fields are server-controlled.

---

## Information Leakage

Notification messages must not expose information to unauthorized recipients.

For example:

A Provider must not receive a notification containing another Provider's private Proposal information.

---

## XSS

Notification titles and messages may contain dynamic data.

Never render them as raw HTML.

User-controlled values must be escaped/sanitized at the rendering boundary.

---

## Data Exposure

Do not place:

- passwords
- access tokens
- refresh tokens
- payment credentials
- private object-storage URLs
- private documents
- sensitive account data

inside notification `data`.

---

## Enumeration

Avoid endpoints that allow a user to determine whether another user's notification exists.

Unauthorized notification access should not expose resource existence.

---

## Rate Limiting

Read endpoints may have normal API limits.

Write endpoints are minimal because normal users do not create Notifications directly.

`mark-all-read` should still be protected against abusive repeated requests.

---

# Notification Ordering

Notifications should be displayed newest first.

```text
createdAt DESC
id DESC
```

Do not rely on database insertion order.

---

# Notification Retention

Phase 1:

Notifications remain stored unless explicitly deleted by an administrative retention policy.

**[Decision]** No automatic notification cleanup is implemented until a retention requirement exists.

---

# Deletion

Do not expose arbitrary user deletion in Phase 1 unless the product specifically requires it.

Marking as read is sufficient for the initial notification center.

Future:

```text
DELETE /notifications/:id
```

can be introduced if notification cleanup is required.

---

# Empty State

The frontend must handle:

```text
0 notifications
```

without mock data.

Example:

```text
You're all caught up.
```

# Acceptance Criteria

The module is considered complete when:

- Notifications can be created internally by the application.
- Users can retrieve only their own Notifications.
- Users can mark their own Notifications as read.
- Users can mark all their Notifications as read.
- Unread count works correctly.
- Notification pagination works correctly.
- Proposal submission generates a Client notification.
- Proposal withdrawal generates a Client notification.
- Proposal acceptance generates a Provider notification.
- Proposal rejection generates a Provider notification.
- Connection establishment generates notifications for both parties.
- Relevant proposers are notified when a Job is cancelled.
- Notification data contains only safe navigation metadata.
- Notification creation does not alter business state.
- Notification failure does not roll back a successful business operation.
- No public notification-creation endpoint exists.
- IDOR and mass-assignment protections are tested.
- No mock notification data exists in the frontend.
- Playwright tests cover the real notification flow.
- API documentation is complete.

# Module Boundary

```text
JOBS
  ↓
Job state changes
  ↓
Domain event
  ↓
NOTIFICATIONS
  ↓
Create in-app notification
  ↓
User reads notification
```

```text
PROPOSALS
  ↓
Proposal submitted
  ↓
NOTIFICATIONS
  ↓
Client notified
```

```text
PROPOSALS
  ↓
Proposal accepted/rejected
  ↓
NOTIFICATIONS
  ↓
Provider notified
```

The architectural rule is:

> **Domain modules own business state. Notifications owns informing users about that state.**

Notifications must never become the source of truth for Jobs, Proposals, Connections, Contracts, Payments, or Reviews.
