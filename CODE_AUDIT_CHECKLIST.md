# Marché — Code Audit Checklist

## 🔴 Broken (produces wrong behavior right now)

- [x] `AppContext.tsx:757-766` (`togglePauseJob`) treats an unpublished draft job as "paused" with no `isDraftPost` check — clicking pause on a draft silently publishes it live instead of pausing it. **Fixed:** added an `if (r.isDraftPost) return r;` guard at the top of the state update, so the function is now a safe no-op on draft jobs regardless of which caller invokes it (the actual bug was `ClientDashboard.tsx:1342`'s Overview-widget `•••` menu calling `togglePauseJob` with no `isDraftPost` check, unlike the main jobs list at line 596 which already excludes drafts).
- [x] `AppContext.tsx:567-572` + `lib/availability.ts:6-11` (`hireVendor`) — "Full Day" and Morning/Afternoon/Evening are independent flags with no conflict check before confirming a hire, so a vendor can be double-booked into overlapping contracts on the same date. **Fixed:** added `isVendorSlotAvailable()` in `lib/availability.ts` — a slot is unavailable if it's already `booked` directly, if a Full Day booking already covers the day, or (for a Full Day request) if any individual slot that day is booked. `hireVendor` now calls this before creating the contract and throws if the vendor is no longer available, matching the existing `!req || !prop` error pattern in the same function.
- [x] `AppContext.tsx:773-776, 778-783` (`deleteJob`, `updateJob`) — audit log `beforeState` is hardcoded (`'Active'` / `'Before Update'`) instead of the job's real prior status, making the admin audit trail factually wrong for these two actions. **Fixed:** both functions now look up the job from state before mutating and log its real `status` as `beforeState`; `updateJob` also logs the actual resulting status (`updates.status` if the update changes it, otherwise unchanged) as `afterState` instead of a hardcoded `'Updated'`.
- [x] `ContractDetailPage.tsx:56-57, 220-237` — `isClient`/`isVendor` are computed but never used to gate the buttons; either role can trigger the other party's "mark complete" / "confirm complete" action. **Fixed:** added `isVendor &&` to the "Mark Event Completed" button condition and `isClient &&` to the "Confirm Completion" button condition, so each action is now only visible/clickable by the party who owns it.
- [x] `ClientDashboard.tsx` — "In Progress" tab count, "Receiving Bids" count, and a "Paused" badge condition (`status === 'Paused'`, which can never be true — see `togglePauseJob` above) all disagree with what actually renders when opened. **Fixed, three parts:**
  - `receivingProposalsCount` now excludes jobs with an active contract (`!hasActiveContract`) instead of just checking `status !== 'Completed'/'Closed'`, matching the actual filter the "proposals" tab uses.
  - The "progress" tab filter now requires an actual contract with `bookingState === 'Confirmed'`, instead of a broken condition that let `'Open'` jobs (never hired) show up under "In Progress" while also including jobs whose contracts were already `Completed`/`Closed`. This now matches the `inProgressContracts` count exactly.
  - Every `req.status === 'Paused'` check (grid card, list card, dropdown Pause/Resume label + toast) replaced with the correct `(!req.isDraftPost && req.status === 'Draft') || req.isPaused` formula (the same one already used correctly elsewhere in the file) — status badges now actually show "Paused" when a job is paused instead of always defaulting to the green/live style.
- [x] `ClientDashboard.tsx:878` (`handleDuplicateJob`) — duplicating a job republishes it live via `createJob` with the original (possibly stale) event date / proposal deadline copied verbatim. **Fixed:** duplication now calls `saveJobDraft(null, {...})` instead of `createJob`, so the copy lands as a draft the client must review and update the date on before publishing, instead of instantly going live with a stale date. Toast message updated to say so; the now-unused `createJob` import was removed from the destructure.
- [x] `ProviderDashboard.tsx:79-97` + `lib/availability.ts:6-11` — `DEFAULT_DAY_AVAILABILITY` defaults "Full Day" to `'blocked'` while the other three slots default to `'open'`, so every untouched future date renders amber "Partially blocked" instead of green "Open." **Fixed:** changed the `'Full Day'` default to `'open'` to match the other three slots — confirmed no other logic (calendar UI, `SLOTS` array, booking/conflict checks) treats "Full Day" as an opt-in-only slot, so this was a plain default-value inconsistency, not intentional behavior.
- [x] `ProviderHomePage.tsx:217` — the `Saved (${savedIds.size})` tab badge counts every job ever saved, but the visible list under that tab is filtered further and can show a different count. **Fixed:** badge now counts `filteredFeed.filter((r) => savedIds.has(r.id)).length` — the exact same computation the "saved" tab uses to render its list, so the number always matches what you see.
- [x] `ProviderHomePage.tsx:177-186` — the promo-card carousel's prev/next arrows and dots have no click handler at all; clicking does nothing, not even a toast. **Fixed:** removed the fake carousel affordance (arrows + dots) entirely — there is only one promo card and no second slide anywhere in the codebase, so building real carousel logic would be scope creep; the honest fix is to not imply a carousel that doesn't exist. Also removed the now-unused `ChevronLeft`/`ChevronRight` imports.
- [x] `ProviderOnboardingPage.tsx:230-244` (`handleFinish`) — uses `value || currentUser.value` fallbacks for title/bio/hourlyRate, so intentionally clearing a field to empty/0 silently keeps the old value instead. **Fixed:** removed the `|| currentUser.X` fallbacks — `title`/`bio`/`hourlyRate` are already seeded from `currentUser` on mount (lines 165, 179-180), so the fallback was redundant and actively harmful; form state is now saved as-is.
- [x] `SubmitProposalPage.tsx:158-170` (`handleSubmit`) — never validates that milestone amounts sum to the bid amount before submitting, despite the UI implying they should reconcile. **Fixed:** added a `milestonesMismatch` check (milestones exist and don't sum to the bid amount) — guarded in `handleSubmit`, disables the Submit button alongside the existing `bidOutOfRange` check, and shows an inline warning next to the "Milestones Total" display, mirroring the existing `bidOutOfRange` UX pattern in the same file.
- [x] `AuthPages.tsx:42` (`handleSignIn`) — role detection checks if the email contains "julian"/"vendor"/"provider", but the actual seeded vendor account's email (`arjun@vermaimagery.com`, `mockData.ts:38`) matches none of those — signing in with the real vendor's own email logs them in as a client. **Fixed:** replaced the dead `'julian'` check with the actual seeded vendor email (`arjun@vermaimagery.com`), kept the `'vendor'`/`'provider'` substring checks for ad-hoc test emails.
- [x] `AdminAuditDashboard.tsx:109-112` vs `:41-47` — the panel explicitly states reviving a Closed/Cancelled state is rejected, but `handleApplyOverride` applies any target state with zero pre-validation — an admin can revive a terminal booking despite the dashboard's own displayed rule. **Fixed at the root:** added a guard directly in `adminOverrideBookingState` (`AppContext.tsx`) that no-ops if the booking's current state is already `Closed` or `Cancelled`, reusing the `oldState` lookup already computed in that function — protects every caller, not just this one UI.
- [x] `App.tsx:180` (`matchRoute` fallback) — any unrecognized route renders `<ClientDashboard />` regardless of the current user's actual role, so a vendor or admin hitting a stale/unmatched link silently gets the client's dashboard. **Fixed:** fallback now checks `currentUser.role` — vendor gets `ProviderHomePage`, admin gets `AdminAuditDashboard`, client keeps `ClientDashboard`.
- [x] `SubmitProposalPage.tsx:104-109` — a `useEffect` (pinning `bidAmount` to `job.budgetMin` for fixed-budget jobs) was called *after* an early `if (!job) return` — a React rules-of-hooks violation (hooks must be called in the same order on every render), found via `eslint` while verifying the items above, not part of the original audit. Confirmed via `git diff` this was already sitting in the uncommitted working tree, not introduced this session. **Fixed:** moved the `useEffect` above the `!job` early return so it's always called unconditionally, with an internal `if (!job) return;` guard instead of relying on the surrounding conditional. Note: a separate, lower-severity lint finding (`react-hooks/set-state-in-effect` — calling `setBidAmount` synchronously inside the effect causes an extra render) surfaced on the same block and is intentionally left unaddressed for now; it's a performance/style suggestion, not a correctness bug like this one was.

## 🟠 Wrongly wired (connected to the wrong thing)

- [x] `AppContext.tsx:302-308, 354-360` (`createJob`, `publishJobDraft`) — "New Matching Job" notification is hardcoded to a single vendor id regardless of category/location match; other vendors, even exact matches, never get notified. **Fixed:** added a `notifyMatchingVendors()` helper that filters `INITIAL_TALENT` (the app's only vendor directory) by category match against the new job and notifies every matching vendor, used by both `createJob` and `publishJobDraft` in place of the hardcoded `'user_vendor_1'`.
- [x] `lib/formatBudget.ts:12` (`isBidWithinBudget`) — only used for a UI warning color in `SubmitProposalPage`; the actual `submitProposal` save action in `AppContext` never calls it, so invalid bids still save fine. **Fixed:** `submitProposal` now throws if the bid is outside the job's budget range (matching the UI's existing warning), same error-throwing pattern already used elsewhere in the function for missing job/proposal. Left `saveProposalDraft` unvalidated on purpose — drafts are allowed to be incomplete/invalid mid-edit.
- [x] `ProviderHomePage.tsx:173` — "Complete Profile" CTA navigates to `/profile/${currentUser.id}` (a read-only public profile sourced from static mock data) instead of `/provider/profile` (the real editable page) — the button meant to fix an incomplete profile can't do anything. **Fixed:** now navigates to `/provider/profile`.
- [x] `SearchJobsPage.tsx:51` vs `ProviderHomePage.tsx:42-43` — each page keeps its own separate `searchQuery` state instead of sharing one from `AppContext`; typing a search on one page has no effect on the other despite looking like the same search bar. **Fixed:** `SearchJobsPage` now destructures `searchQuery`/`setSearchQuery` from `useApp()` instead of a local `useState`. Verified live: typing "catering" on Search Jobs and switching to Home via the sidebar (SPA nav, not a reload) shows the same text in Home's search box.
- [x] `App.tsx:48-181` (whole route dispatcher) — no check anywhere consults `currentUser.role`; any signed-in role can reach any other role's route (including `/admin/audit`, the force-override tool) just by navigating directly to the URL — the sidebar only hides links, it doesn't gate destinations. **Fixed:** added a shared `roleHome()` helper (also replacing the item-25 fallback's duplicated logic) and role guards at the top of `matchRoute()` for the `/admin/`, `/client/`, and `/provider/` prefixes, plus the `/provider/onboarding` and `/client/onboarding` checks above it — any mismatched role gets redirected to its own home instead of rendering the other role's page. One deliberate exception: `/provider/dashboard` stays open to admin too, since admin's own "Jobs" nav link (kept from the item-35 fix) intentionally reuses that page. Shared read-only routes (`/profile/:id`, `/contracts/:id`, `/messages`, `/notifications`, `/menu`) were left ungated since they're legitimately used by more than one role. Verified live across all 3 roles × mismatched-route combinations (vendor→client/admin routes, client→provider/admin routes, admin→provider routes other than the dashboard exception) — every case redirected correctly, confirmed via screenshots.
- [x] `Sidebar.tsx:118-123, 141-146` — admin nav's "Client Dashboard" and profile fallback links route to pages that filter by the current user's own id; since the admin's id matches no job/contract/talent record, both links always render empty/"not found." **Fixed:** removed the "Client Dashboard" nav item entirely (no coherent admin-facing destination exists for it — building an admin-aware data path into `ClientDashboard.tsx` was judged out of scope/over-engineering for a nav-link fix). Added a real `/admin/profile` route in `App.tsx` reusing the same `EditProfilePage` component already shared by `/client/profile` and `/provider/profile` (confirmed it has only one role check, `isVendor`, so it's safe for the admin role too), and pointed the sidebar's profile fallback at it instead of the broken `/profile/${currentUser.id}`. **Re-check found this exact bug duplicated in two more places** (not part of the original audit — found while re-verifying this item): `MobileMenuPage.tsx:33` had the identical broken `` `/profile/${currentUser.id}` `` fallback (now `/admin/profile`, same as Sidebar), and `MobileTabBar.tsx:29` had its own separate admin tab array with a dead `"Clients" → /client/dashboard` entry (now removed, same reasoning as the Sidebar fix). Verified live: admin's mobile-menu identity card now opens `/admin/profile` correctly, the bottom tab bar no longer shows "Clients," and editing the admin's bio and saving survives a full page reload (confirms `updateCurrentUser` persists correctly for the admin role, not just client/vendor).
- [x] `ProviderHomePage.tsx:44-45` vs `SearchJobsPage.tsx:53` — the "filter jobs by category" feature is modeled two incompatible ways (a global single-value filter vs. a separate local multi-select set) between two pages that should share it. **Fixed without redesigning either page's UI:** kept Home's existing single-select-style checkboxes and Search Jobs' existing true multi-select checkboxes as-is, but bridged the underlying state — Search Jobs' category set now seeds itself from the shared `selectedCategoryFilter` on mount, and a `toggleCategory()` helper mirrors changes back into the shared value (one category selected → that category; zero or several → `'All'`, since a single value can't represent an ambiguous/multi selection). Verified live: selecting "Catering" on Search Jobs correctly filtered Home's feed down to just the catering job, with the Filters button showing its active-filter indicator dot.

## 🟡 Misplaced (logic sitting in the wrong layer)

- [x] `VendorProfilePage.tsx:73, 93, 105, 115-117` — the entire public profile page is sourced from static mock arrays (`INITIAL_TALENT`, etc.) and never reads `currentUser`; edits made via onboarding/`EditProfilePage` never show up on a vendor's own public profile. **Fixed:** when `id === currentUser.id` (viewing your own profile), the mock `talent` record is now overlaid with `currentUser`'s live name/avatar/headline/bio/location/hourlyRate/skills/verified — other vendors' profiles are untouched and still render pure mock data (there's no live data source for anyone else, given no backend). Only overrides fields that are actually editable via onboarding/`EditProfilePage`; portfolio/testimonials/work-history/project-catalog stay mock-sourced since nothing in the app lets a vendor edit those. Verified live: editing the bio via `/provider/profile` and saving showed the new bio on `/profile/user_vendor_1` immediately, while `/profile/user_vendor_2` (a different vendor) still showed unrelated, untouched mock data.
- [x] `ProviderHomePage.tsx:48-54` vs `ClientDashboard.tsx:76-79` — the "is my profile complete" rule is independently reimplemented per page instead of centralized, risking silent drift between client and provider criteria. **Fixed:** added `lib/profileCompleteness.ts` with a single `isProfileComplete(user)` function that branches internally on `user.role` (vendor additionally requires a positive `hourlyRate`, preserving the intentional per-role difference — this wasn't a bug, just duplicated logic) — both pages now import it (aliased to avoid colliding with their existing local variable name of the same name) instead of each reimplementing the check inline. Verified live: the incomplete-profile banner still correctly disappeared once all required fields were filled.
- [x] `AppContext.tsx:611-647, 650-686` (`vendorMarkCompleted`, `clientConfirmCompletion`) — the only guard against invalid booking-state transitions lives in `ContractDetailPage.tsx`'s button conditions, not in these state-owning functions themselves, which will execute unconditionally on any `contractId` regardless of current state. **Fixed:** added `ctr.bookingState !== 'Confirmed'` / `!== 'Completed'` guards directly in each function (no-op otherwise), matching the same defense-in-depth pattern used for `togglePauseJob`, `hireVendor`, and `adminOverrideBookingState` earlier in this session. Verified live: the full vendor-marks-complete → client-confirms flow still works end to end, reaching the terminal "Lifecycle Complete" state with no regression.
- [x] `MessagesPage.tsx:55` — `favoriteIds` (favorited conversations) lives only in local component state instead of `AppContext`/localStorage like everything else in the app; navigating away and back loses the favorite. **Fixed:** moved favorites into `AppContext` as `favoriteConversationIds: string[]` + `toggleFavoriteConversation()`, persisted to localStorage the same way as `jobs`/`contracts`/`messages`. Verified live: favorited a conversation, navigated away to Notifications and back via the sidebar (a real unmount/remount, not just a state change) — the star stayed on the conversation row and the "Favourites" tab still showed it.
