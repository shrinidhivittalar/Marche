## 🔴 Broken (produces wrong behavior right now)

- [x] `AppContext.tsx:757-766` (`togglePauseJob`) treats an unpublished draft job as "paused" with no `isDraftPost` check — clicking pause on a draft silently publishes it live instead of pausing it. **Fixed:** added an `if (r.isDraftPost) return r;` guard at the top of the state update, so the function is now a safe no-op on draft jobs regardless of which caller invokes it (the actual bug was `ClientDashboard.tsx:1342`'s Overview-widget `•••` menu calling `togglePauseJob` with no `isDraftPost` check, unlike the main jobs list at line 596 which already excludes drafts).
- [x] `AppContext.tsx:567-572` + `lib/availability.ts:6-11` (`hireVendor`) — "Full Day" and Morning/Afternoon/Evening are independent flags with no conflict check before confirming a hire, so a vendor can be double-booked into overlapping contracts on the same date. **Fixed:** added `isVendorSlotAvailable()` in `lib/availability.ts` — a slot is unavailable if it's already `booked` directly, if a Full Day booking already covers the day, or (for a Full Day request) if any individual slot that day is booked. `hireVendor` now calls this before creating the contract and throws if the vendor is no longer available, matching the existing `!req || !prop` error pattern in the same function.
- [x] `AppContext.tsx:773-776, 778-783` (`deleteJob`, `updateJob`) — audit log `beforeState` is hardcoded (`'Active'` / `'Before Update'`) instead of the job's real prior status, making the admin audit trail factually wrong for these two actions. **Fixed:** both functions now look up the job from state before mutating and log its real `status` as `beforeState`; `updateJob` also logs the actual resulting status (`updates.status` if the update changes it, otherwise unchanged) as `afterState` instead of a hardcoded `'Updated'`.
- [x] `ContractDetailPage.tsx:56-57, 220-237` — `isClient`/`isVendor` are computed but never used to gate the buttons; either role can trigger the other party's "mark complete" / "confirm complete" action. **Fixed:** added `isVendor &&` to the "Mark Event Completed" button condition and `isClient &&` to the "Confirm Completion" button condition, so each action is now only visible/clickable by the party who owns it.
- [x] `ClientDashboard.tsx` — "In Progress" tab count, "Receiving Bids" count, and a "Paused" badge condition (`status === 'Paused'`, which can never be true — see `togglePauseJob` above) all disagree with what actually renders when opened. **Fixed, three parts:**
  - `receivingProposalsCount` now excludes jobs with an active contract (`!hasActiveContract`) instead of just checking `status !== 'Completed'/'Closed'`, matching the actual filter the "proposals" tab uses.
  - The "progress" tab filter now requires an actual contract with `bookingState === 'Confirmed'`, instead of a broken condition that let `'Open'` jobs (never hired) show up under "In Progress" while also including jobs whose contracts were already `Completed`/`Closed`. This now matches the `inProgressContracts` count exactly.
  - Every `req.status === 'Paused'` check (grid card, list card, dropdown Pause/Resume label + toast) replaced with the correct `(!req.isDraftPost && req.status === 'Draft') || req.isPaused` formula (the same one already used correctly elsewhere in the file) — status badges now actually show "Paused" when a job is paused instead of always defaulting to the green/live style.
- [x] `ClientDashboard.tsx:878` (`handleDuplicateJob`) — duplicating a job republishes it live via `createJob` with the original (possibly stale) event date / proposal deadline copied verbatim. **Fixed:** duplication now calls `saveJobDraft(null, {...})` instead of `createJob`, so the copy lands as a draft the client must review and update the date on before publishing, instead of instantly going live with a stale date. Toast message updated to say so; the now-unused `createJob` import was removed from the destructure.
- [x] `ProviderDashboard.tsx:79-97` + `lib/availability.ts:6-11` — `DEFAULT_DAY_AVAILABILITY` defaults "Full Day" to `'blocked'` while the other three slots default to `'open'`, so every untouched future date renders amber "Partially blocked" instead of green "Open." **Fixed:** changed the `'Full Day'` default to `'open'` to match the other three slots — confirmed no other logic (calendar UI, `SLOTS` array, booking/conflict checks) treats "Full Day" as an opt-in-only slot, so this was a plain default-value inconsistency, not intentional behavior.
- [x] `ProviderHomePage.tsx:217` — the `Saved (${savedIds.size})` tab badge counts every job ever saved, but the visible list under that tab is filtered further and can show a different count. **Fixed:** badge now counts `filteredFeed.filter((r) => savedIds.has(r.id)).length` — the exact same computation the "saved" tab uses to render its list, so the number always matches what you see.
- [x] `ProviderHomePage.tsx:177-186` — the promo-card carousel's prev/next arrows and dots have no click handler at all; clicking does nothing, not even a toast. **Fixed:** removed the fake carousel affordance (arrows + dots) entirely — there is only one promo card and no second slide anywhere in the codebase, so building real carousel logic would be scope creep; the honest fix is to not imply a carousel that doesn't exist. Also removed the now-unused `ChevronLeft`/`ChevronRight` imports.
- [x] `ProviderOnboardingPage.tsx:230-244` (`handleFinish`) — uses `value || currentUser.value` fallbacks for title/bio/hourlyRate, so intentionally clearing a field to empty/0 silently keeps the old value instead. **Fixed:** removed the `|| currentUser.X` fallbacks — `title`/`bio`/`hourlyRate` are already seeded from `currentUser` on mount (lines 165, 179-180), so the fallback was redundant and actively harmful; form state is now saved as-is.
- [x] `SubmitProposalPage.tsx:158-170` (`handleSubmit`) — never validates that milestone amounts sum to the bid amount before submitting, despite the UI implying they should reconcile. **Fixed:** added a `milestonesMismatch` check (milestones exist and don't sum to the bid amount) — guarded in `handleSubmit`, disables the Submit button alongside the existing `bidOutOfRange` check, and shows an inline warning next to the "Milestones Total" display, mirroring the existing `bidOutOfRange` UX pattern in the same file.

- [x] `SubmitProposalPage.tsx:104-109` — a `useEffect` (pinning `bidAmount` to `job.budgetMin` for fixed-budget jobs) was called *after* an early `if (!job) return` — a React rules-of-hooks violation (hooks must be called in the same order on every render), found via `eslint` while verifying the items above, not part of the original audit. Confirmed via `git diff` this was already sitting in the uncommitted working tree, not introduced this session. **Fixed:** moved the `useEffect` above the `!job` early return so it's always called unconditionally, with an internal `if (!job) return;` guard instead of relying on the surrounding conditional. Note: a separate, lower-severity lint finding (`react-hooks/set-state-in-effect` — calling `setBidAmount` synchronously inside the effect causes an extra render) surfaced on the same block and is intentionally left unaddressed for now; it's a performance/style suggestion, not a correctness bug like this one was.
